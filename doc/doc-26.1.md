# 更新速览

相比上个版本, Wolfarch Logic System 发生了重大改动

1. 版本号格式异动. 现在正式版采用**年份后两位 + . + 更新次数**来记录版本. 开发中版本采用**年份后两位 + W/S (分别表示冬季和夏季学期) + 周 + 更新次数(字母表示)**, 或者采用**年份后两位 + W/S (分别表示冬季和夏季) + B + 更新次数(字母表示)**表示寒暑假期间的开发. 例如正式版可能看起来像是 `26.1`, 测试版可能是 `26S15a` 或者 `26WBb`.

2. 功能发生变化. 
  - 现在报错信息可以在 `config.h` 中修改. 而在最大长度等配置信息现在不再能具体配置(因为现在长度和深度近似于无限). 但是需要手动配置分配内存的量. 
  - WLS 本身语法发生变化. 原本的代码将无法运行. 
  - 现在不再支持自动安装
  - 添加 `surrender` 关键字, 可以跳出证明过程. 
  - 添加 `empty` 关键字, 现在可以强制清空当前关键字作用域. 而 import/given 现在更加严格. 只能在 import/given 作用域之间切换. 因此, 现在开头的默认关键字为 `import`, 而不再是 `empty`. 如果要立刻开始操作而不依赖于任何背景, `empty` 就很有用.

3. 代码重构
  - 修改了代码格式.
  - 针对内存管理系统进行更加激进设计. 现在整个程序运行时只会在开始阶段分配一块较大内存. 
  - 移除了所有结构体中的指针项, 这是为了节约内存. 现在统一使用 `unsigned int` 表示指针. 
  - 被反复调用的结构, 比如 `CURR_SYSTEM`, 以及新增的统一内存池 `MEM_BASE`, 为了避免反复传递而全局化. 
  - 因为使用条件比较苛刻, 代码中的所有函数指针被清理. 
  - 现在只有哈希塔, 哈希集合的节点采用节点型内存池分配. 原本的用户输入, 层管理器, 命题, 事实等, 改为使用栈式分配 (不是真的在栈上分配). 
  - 修改了节点型内存池的实现方法, 现在更为简单. 
  - 修改用户输入 (或者读取文件输入) 到解析的步骤. 现在不再过于丑陋.

## 26.1 内存结构

### 全局区

- `CURR_SYSTEM` (类型: `WLS`)
  存储所有的哈希集合, 哈希塔, 层管理器. 并掌管堆内存块的每一个关键节点. 

- `MEM_BASE` (类型: `char*`)
  隐匿于 `OFF` 和 `PTR` 之后, 全局堆内存区的起点.

### 栈区

仅存储一些小局部变量. 没有大数组. 由于 WLS 没有递归函数, 栈区使用非常少. 

### 堆区

核心数据存储区域, 被井井有条分划为几个区域. 堆区默认640KB. 

1. **I 区: 哈希表桶数组**

默认占据40KB, 依次存放:

- `controller` 层控制器对应已使用层哈希集合的桶, 默认256B, 64个桶槽位
- `fact_set` 哈希塔的桶, 默认占据20KB, 5088个桶槽位. 
- `used_paras` 哈希塔的桶, 默认占据10KB, 2544个桶槽位.
- `prop_table` 哈希塔的桶, 默认占据10KB, 2544个桶槽位.

2. **II 区: 节点内存池**

默认占据80KB, 依次存放:

- `pool_for_sets` 内存池的对应节点. 用于存储 `controller` 对应已用层哈希集合的节点. 默认占据256B, 最大32节点
- `pool_for_towers` 内存池的对应节点, 用于存储三个哈希塔的节点. 默认占据80KB, 最大5088节点.

3. **III 区: 开放栈**

占据堆区剩余的全部空间 (大约520KB)

存储很多个手动管理的栈区. 当创建新 `context_t` 时候, 总是伴随推栈, 撤除 `context_t` 时候, 总是伴随压栈. 

每一个栈的开头可能有一个命题或者事实, 随后是两个总共占据 `2 * sizeof(void*)` 字节的指针, 指向上一个栈区的两个起点. 第一个指针所指向的**前起点**是命题或者事实的起点, 按前起点压栈会吞掉这个命题或者事实, 用于失败情况下的压栈. **后起点**则位于命题或者事实的终点的下一格, 即指向再前一个栈的前期点的指针. 按后起点压栈会自动视作这个命题或者事实无缝衔接在前一个栈的末尾. 

之所以叫做开放栈, 因为可以随意分配大小, 需要多少空间就可以分配多少空间, 于是最大用户输入长度就可以非常长, 空间消耗却不会非常多.

下列内容均从栈顶分配.  

- 用于存储用户输入字符串的空间. 
- 解析事实定义式, 或解析命题调用式得到的命题字符串. 
- 解析命题定义式得到的命题本身.
- 解析命题定义式, 或者解析存在命题调用式得到的名字.
- 哈希塔层控制器的层.

这会导致一些行为上的变化. 当压栈块的时候. 哈希塔中的一些节点的`key` 和 `value` 可能已经损毁 (因为哈希塔基于字符串浅拷贝). 不过只要先检测节点所在层是否已经被删除就可以解决问题. 因为被销毁的栈必然对应着一个被剔除的层号. 这时就可以安心地覆盖节点, 甚至不需要像原来地版本中考虑如何释放这些键和值 (因为它们已经伴随压栈瞬间释放了). 

这个改动极大节约了内存. 在先前的版本中, 这些内容全靠内存池分配, 导致一条命令的长度限制非常苛刻, 而且即使命令平均都很短, 也需要用掉大量的空间. 

## 新语法

1. 存在命题不再可以先声明再证明, 必须先推导再证明. 全称命题规则不变. 证明存在命题的尝试现在总是立即得到结果 (证明出和无法证明出). 
2. 命题定义式中的参数现在要用大括号括起来. 但是矛盾的是, 不能对 "any: " 或者 "exist: " 后的参数列表里的参数加大括号. 
3. 现在要引用构造量, 必须用方括号括起来, 否则无法引用. 
4. 新增关键字: `surrender`, 可以跳出当前背景. 如果根本没有这样的背景, 则什么也不会发生. 新增关键字: `emtpy`, 可以强行把目前关键字置为 `empty`

# 简介

WLS是一个简单的形式证明系统. 

# 基本语法和特性
WLS是解释性语言, 写一行, 运行一行. 也可以批量运行, 但本质上也是一行一行的运行.

命令可以分为[关键字命令](#关键字)和普通命令两种.
- 关键字命令: 结尾必须是":", 即使后面写的是"#"开始的注释, 也必须写冒号.
- 普通命令: 用句点+井号结尾, 或者注释结尾. 

需要注意的是, 在此系统中, **一行并不一定是读到回车算一行, 少数情况下, 明明视觉上写了好几行, 实际上却会被合并为一行.**
行结束的标识有以下几种:
- "."后紧跟换行.
- ":"后紧跟换行.
- "#"

例:
```python
import:
宇宙真理(any:):主=6.
空(any:):. # 注意, 如果命题没有结论, 也不能直接写":"+"#", 否则会被当成关键字命令. 
given:
一个特别特别特别特别特别特别特别特别特别
特别特别特别特别特别特别长的事实.
# 上面"两行"在语法解析器里看来是连起来的
一个事实 # 注意前面不写句号.
另一个事实. # 写了句号也可以, 注释结尾想不句号就不句号
```

关于缩进:
WLS不严格要求缩进. 因为在命令行的语法解析中, 一切空格实际上是被忽略的. 但是**我们强烈建议在prove和suppose内缩进**, 建议的风格如下:
例:
```python
import:
f1(any:):.
f2(exist:):. # import下, 不缩进
given:
事实1.
事实2 # given下也不缩进
prove:
一个命题(any:):... # prove下先不缩进
  # 从命题声明完的下一行开始缩进, 通常2个空格或者4个空格.
  # ...证明过程
  # prove. (最后这里最好写一个这样的注释, 说明证明结束. )
  # (尤其是不缩进的情况下, 这一条非常重要, 别的都可以不写就这个必须写)
suppose: # 恢复到正常缩进
xxx事实 # suppose和prove也是一样的道理
  # ...证明过程
  # suppose end. ("proved."和"suppose end."可以随便写, 不是什么固定关键字, 但通常写成这样.)
```

**和数学中普遍约定的名词解释可能不同, 需要确保理解这种差异.**

## 关键字
所有关键字都以":"结尾, 并且作用域都开始于关键字所在行的下一行. 这意味着你必须输入关键字之后, **切换到下一行**, 不然你的内容会被忽略.
例:
```python
prove:
世界真理(any:):1+1=2 # 正确, 应当把东西写在关键字下一行
  prove: 宇宙真理(any:): 主=6 # 错误, 冒号后的部分会被忽略
```
### import
公理化引入命题的唯一办法. 是证明的基础. 没有公理就啥也干不了.
import关键字下, 可以任意使用[命题定义式](#命题定义式)引入公理命题. 一行一个命题定义式. 这些命题会被直接加入系统.
例:
```python
import:
世界真理(any:)1+1=2.
宇宙真理(any:)主=6.
```
import 关键字在开始证明之后就不能再使用了. 这是为了让基本假设和证明步骤能够分离. 

### given
[import](#import)可以公理化的引入命题, given则可以用于公理化的引入[事实]. 
given作用域下, 随便写字, 直到出现"."接"\n"或者"#", 在此两者之前的内容都会被识别为事实字符串的内容. 然后加入事实库.
例:
```python
given:
1+1=2.
# 识别到的事实为"1+1=2", 而不是"1+1=2."
主=6 # 识别到的事实为"主=6"
```
和import一样, 它不能在证明过程当中使用, 其作用域无限长.

### prove
用于开始证明. prove的作用域仅一行. 
在prove下, 需要写一个[命题定义式](#命题定义式). 表示要证明的命题.
例:
```python
prove:
f(any:):六神无主是ABCA式的成语.
  # 证明过程...(此处的命令不属于任何一个关键字的作用域)
```
prove和[suppose](#suppose)是唯二的可以创造一片不属于任何关键字作用域的空间. 而那是[命题调用式](#命题调用式)唯一发挥作用的地方.

### suppose
用于开始假设. 与[prove](#prove)一样, 作用域仅一行.
在suppose下, 需要写一个命题. 
事实上由于命题就是字符串, 你可以随意写. 类似于[given](#given), 但仅写一条, 表示假设的事实.
例:
```python
suppose:
1=0.
  # 过程...(此处的命令不属于任何一个关键字的作用域)
```
[prove](#suppose)和suppose是少数的可以创造一片不属于任何关键字作用域的空间. 而那是[命题调用式](#命题调用式)唯一发挥作用的地方.

### quit
0.3版本加入的新关键字. 在以前的wolfarch控制台模式中, 输入quit也可以退出. 但是由于系统自带的不读到句号或者注释不停下的特点, 必须要输入"quit."或者"quit#"才可以退出. 甚至"quit:"由于在当时会被识别为关键字, 所以无法退出. 现在前两种方法已经失效, 而quit也正式成为了一个关键字. 执行这个关键字的后果就是让系统全局退出, 并且在控制台模式和文件模式均能正常运行.

### surrender
26.1 新增关键字. 遇到不会的证明但是跳不出来? surrender 可以解决你的问题. 无损跳出, 一干二净什么也不剩: 直接回到还没有进行这个证明或者进行这个假设的状态下. 然后你就可以考虑是否应该在外面多进行一些推导. 

### empty
26.1 新增关键字. 被卡在 import 或者 given 的关键字, 结果没有东西可以证明, 又不想用 prove 或者 suppose 的报错硬启动? 可以使用 empty 关键字. [命题调用式](#命题调用式) 只能在这样的区域发挥作用. 这个关键字专门切断关键字作用域, 非常快捷高效和方便.

### debug
这不是一个标准的关键字. 但是看到 quit 这样的东西都能成为关键字, 它在 26.1 版本也成为了一个正式的关键字, 即使它的历史已经非常久远. 可以打印一个丑陋的调试页面. 

## 事实
一个字符串. 内部的空格被忽略.
例:
```python
"1+1=2"
"0是自然数"
"苏格拉底是人"
"人会死"
"花是红的,草是绿的"
"太阳是绿色的"
"水是剧毒的"
"2不是偶数"
```
事实是否成立取决于是否位于系统中. 

## 命题
一个命题一般被看做是一个类(或者结构体, 数据块之类的)的实例.

一个命题有这些字段:

- 名字: 一个字符串
- 参数: 一个装了很多个字符串的列表
- 条件: 一个装了很多字符串(实际上是事实)的列表
- 结论: 一个装了很多字符串(实际上是事实)的列表
- 类型: 两种, 存在命题或者全称命题.

### 命题定义式
一条固定结构的命令, 用于[关键字](#关键字)"prove:"和"import:"后.

命题定义式可以表达一个命题. 

例:
```python
等式交换律(any: x, y) {x}={y}: {y}={x}.
人会死(any: man) {man}是人: {man}会死.
存在偶数(exist: n): {n}是偶数.
存在父亲(any: man) {man}是人: ((exist: father): {father}是{man}的父亲).
数学归纳原理(any: f) {f}(1), ((any: k) {k}是正整数, {f}({k}): {f}({k}+1)): ((any: n) {n}是正整数: {f}({n})).
```

### 命题核心表达式
命题核心表达式是一个事实. 征得命题核心表达式是证明命题的一个重要方法. 

如果命题定义式完整定义了一个命题, 命题核心表达式则表示了一堆命题. 实际上, 命题核心表达式就是命题定义式去掉了括号剩下的部分. 

这些都是命题核心表达式.

```python
(any: x, y) {x}={y}: {y}={x}.
(any: man) {man}是人: {man}会死.
(exist: n): {n}是偶数.
(any: man) {man}是人: ((exist: father): {father}是{man}的父亲).
(any: f) {f}(1), ((any: k) {k}是正整数, {f}({k}): {f}({k}+1)): ((any: n) {n}是正整数: {f}({n})).
```

命题核心表达式证明命题让嵌套命题和实现复杂的逻辑成为可能. 

### 命题调用式
一条固定结构的命令. 包含一个命题名, 和准备填入的示例参数. 它的用途是"使用"已经存在于系统中的命题. 

解析命题调用式的同时也会根据调用的命题对系统进行操作, 比如通过已知的东西推导得到为止的东西. 

对于全称命题, 调用它们的步骤大概是:
- 把调用参数填入前提部分.
- 检查是否全都位于系统中
- 如果位于系统中, 则把调用参数填入结论部分, 然后将这些结论加入系统. 

对于存在命题, 调用的方法则不同:
- 检查每个参数是否已经被其他存在命题调用过.
- 如果都没有被调用过, 需要给每个参数起一个名字. 这些名字是系统自动生成的, 每个参数都不一样. 
- 把参数的新名字填写进结论部分, 然后把这些结论加入系统. 

命令的基本结构是: 名字(实例). 结尾是"句号+换行"或者"#"
例:
```python
等式交换律(a, b).
人会死(苏格拉底).
存在偶数(k).
```

对于具体的调用式行为案例分析, 可以去后面的[案例分析](#具体案例分析)看.

## 证明

### 证明开始

证明是一个有趣的操作, 可以得到新的命题. 但是机制非常复杂. 

当你在关键字 `prove` 后一行输入一个语法正确的命题定义式的时候, 系统就知道你要准备证明什么命题了. 然后开始检测.

对于全称命题和存在命题完全是两套不一样的机制. 然而, 它们共享一个第一步: 

1. 检查这个命题的命题核心表达式是否位于系统中. 如果在系统中, 证明完毕. 参见[证明结束](#证明结束)

然后这两者就不一样了. 我们先解释全称命题.

2. a. 将这个命题的参数填入这个命题的前提中, 然后把每个替换后前提加入系统. 

例如这个证明: 
```python
prove:
q(any: P) {P}, ->({P}, Q): Q.
```

会立刻把 "P" 和 "->(P, Q)" 加入系统, 而不是 "{P}" 和 "->({P}, Q)". 所以 "把待证明命题的前提加入系统" 这个说法不够准确. 

3. a. 然后就结束了. 但是证明并没有结束, 而是才刚刚开始. 此时只是将一个初始条件加入系统, 而并没有真正证明这个命题. 还得接下里进行一些命题调用的操作, 不断增加事实的数量, 才能证明这个命题. 但是这部分内容主要在[证明结束](#证明结束)里说明. 

然后解释存在命题. 

2. b. 首先, 检查每一个参数是否都曾经被一个存在命题所引用. 也就是说, 准备证明的参数都应该具备一个系统给它生成的名字. 如果有一个参数没有, 直接证明失败. 什么也不发生, 否则继续.

3. b. 其次, 根据每一个参数的名字, 填入命题的结论部分. 然后进行检查. 如果被替换后得到的结论并没有在系统中那个, 直接证明失败. 否则证明成功, 跳转到[证明结束](#证明结束)

例如, 这个存在命题证明成功了, 因为它发现 obj 曾经被调用. 假设系统给 "obj" 取的名字是 "CON 0", 那么, 
`猫是动物([obj]). ` 这一句就已经把 "CON 0是动物" 加入了系统. 这正是系统所检查的结论, 所以证明成功. 

```python
import:
猫是动物(any: obj) {obj}是猫: {obj}是动物.
存在猫(exist: obj): {obj}是猫.
empty:
存在猫(obj).
猫是动物([obj]).
prove:
存在动物(exist: obj): {obj}是动物.
```

### 证明结束

#### 证明成功的检验

*这里仅限全称命题*

存在命题一旦开始证明就只有成功和失败两个结果, 但是全称命题没有直接成功, 可以延迟成功 (现在加入 surrender 关键字后还可以延迟失败). 所以什么时候成功是需要一直检查的. 

每有一条有效的非关键字命令输入 (不包括空行, 注释这些), 系统就检查: 

1. 在证的这个命题, 它的核心命题表达式在系统中吗? 
2. 在证的这个命题, 它的结论都被证明了吗? 

要是两点都达成, 那就证明完毕. 

有一点要注意, 和前面的 "前提加入系统" 一样, 这个结论也并不是定义式中的原始结论字符串, 而是去掉了每个参数的大括号的. 

#### 证明成功之后做的事

证明成功主要有这些来源:

1. 上面的 [全称命题的延迟检验](#证明成功的检验)
2. 命题核心表达式直接在系统中
3. 存在命题证明成功

两种命题依旧有差异. 不过它们的第一步还是一样. 

1. 将命题加入系统
2. 将命题的核心表达式加入系统

注意, 这里可能有一个 bug, 从命题核心表达式证得的命题, 核心表达式已经位于系统中, 此时相当于重复插入, 系统需要有一个手段来避免爆炸和不正确的行为. 

对于全称命题:

3. a. 删掉所有自证明以来, 加入系统的命题, 事实和期间调用存在命题生成的参数->名称对应关系. 这包括了刚刚启动证明时候往系统里面添加的初始条件. 

*一下子删掉所有的命题可能比较困难, 对此, 系统实际上采用 "给命题等内容标号" 的方法, 直接删掉标号, 就当作删掉了所有的对应内容, 但是这个是具体实现细节, 并不是语言标准.*

对于存在命题

3. b. 删掉证明完成的表达式中的所有参数的名称. 

## 假设

反证比证明简单. 

suppose 后跟着的东西就是你要假设的内容. 然后类似于全称命题证明, 它不会立即结束, 而是将假设先添加入系统, 从而让你能够推导. 

假设结束的标识也与全称命题证明非常相似, 但是唯一检查的就是一个矛盾标识. 必须由解释器规定一个全局唯一, 对于所有证明中都通用的矛盾标识. 

假设结束之后, 将假设的内容的否加入系统. 至于怎么表达假设内容的否, 这也需要由具体的解释器规定. 

用户需要自行引入合理的产生矛盾标识的命题, 从而使得反证法能够运行. 

## 命令自动替换

可以看到, 每次调用"存在"命题, 系统都会生成一个对应的名字, 并且添加到事实库中的也是以生成的名字为准的, 那该如何引用它呢? 这就需要用到命令自动替换. 在 26.1 版本后, 命令在输入阶段就会对构造量进行拦截. 标识就是中括号`[]`. 

具体的, 当解析器看到形如 `[xxx]` 的结构时, 便检查是否有 "xxx -> 构造量" 位于系统的 "已使用参数表" 中. 如果找到了, 那就将整个 "[xxx]" 替换为对应的构造量. 例如, "xxx" 对应 "CON 100", "[xxx]" 就会被替换为"CON 100". 这完全在输入阶段完成, 早于任何的解析步骤. 

# 令人红温的括号

WLS 粗暴的吞噬了所有的空格, 导致区分语法非常困难, 括号的重任于是极其艰巨, 虽然足够灵活, 但是还是会导致一些问题. 

命题调用式里通常有很多的括号, 在命题嵌套的复杂场景, 括号非常必要. 但是一定需要牢记括号的解析顺序. 

命题调用式解析的步骤是: 先按括号分块(哪里是参数, 哪里是条件, 哪里是结论等), 然后每个块去掉括号, 对内部进行再按括号分块. 

这导致了一些情景下, 需要写看起来诡异的命题定义式. 

例如:
```python
-1(any: x) rat({x}): ((exist: a, b): int({a}), int({b}), n0({b}), !(and(eve({a}), eve({b}))), =({x}, /({a}, {b}))),.
```

这一句最后句号前的逗号是必要的, 否则, 系统先进行区域分块. `((exist: a, b): int({a}), int({b}), n0({b}), !(and(eve({a}), eve({b}))), =({x}, /({a}, {b})))` 是一块, 发现外层有括号, 去掉变成 `(exist: a, b): int({a}), int({b}), n0({b}), !(and(eve({a}), eve({b}))), =({x}, /({a}, {b}))` , 然后按逗号解析, 就会很错误地截断为 ``(exist: a, b): int({a})` 等好几个部分, 那就炸缸了. 这实际上只是一个结论, 而不是很多个. 

只需要牢记, 如果命题定义式的一个部分只有一个前提, 或者一个结论, 而且这个前提或者结论字符串里有逗号, 必须在前面或者后面补逗号, 不影响分块, 但是破坏掉整块去括号的进程, 从而维持住内容的完整性. 

中括号和大括号则没有什么问题. 

当它们内部包围有东西的时候, 如果里面的东西可以被替换, 它们会随着被替换, 否则, 它们就是正常字符, 并不会导致错误. 

另外还有一点规则, 中括号和大括号并不能嵌套. 谁在外面, 里面的东西就失效. 大括号嵌套大括号也不行, 中括号嵌套中括号也不行. 

# 具体案例分析

我们结合一个具体案例讲解 WLS 的工作原理

```python

后继更大(any: num) {num}是整数: {num}+1>{num}, {num}+1是整数. # 定义公理命题

    有最大整数(exist: num): {num}是整数, ((any: m) {m}是整数: !({m}>{num})).
    # 进行检查: "A_CONFLICT_HAS_OCCURRED!" 位于系统中吗? 不在, 所以继续.

    有最大整数(N).

    # 将 CON 0 替换进这个命题的结论部分, 即"CON 0是整数", "((any: m) {m}是整数: !({m}>CON 0))" 这两个事实加入系统.
    # 进行检查: "A_CONFLICT_HAS_OCCURRED!" 位于系统中吗? 不在, 所以继续.
    prove:
    N最大(any: m) {m}是整数: !({m}>[N]).
    # 这个式子在系统看来, 被识别为"N最大(any: m) {m}是整数: !({m}>CON 0)", 因为 N 外面有中括号, 自动根据对应关系替换. 
    # 启动证明.
    # 检验事实 "(any: m) {m}是整数: !({m}>CON 0)" 是否存在于系统中, 发现找到了, 证明完毕. 
    # 将命题 "N最大" 和事实 "(any: m) {m}是整数: !({m}>CON 0)" 加入系统, 发现后者已经存在, 但是没有关系, 仅仅插入失败, 并没有爆炸. 
      # prove.
    # 进行检查: "A_CONFLICT_HAS_OCCURRED!" 位于系统中吗? 不在, 所以继续.
    后继更大([N]).
    # 这个式子在系统看来, 被识别为 "后继更大(CON 0)"
    # 调用 "后继更大" 这个命题. 这是一个全称命题, 需要进行检查. 
    # 将参数填入命题的前提部分, 即 "{num}是整数", 其中 num 是 CON 0, 得到的是 "CON 0是整数". 发现找到了. 所以继续.
    # 将参数填入命题的结论部分. 类似的, 得到的是 "CON 0+1>CON 0" 还有 "CON 0+1是整数", 并将它们加入系统. 
    # 进行检查: "A_CONFLICT_HAS_OCCURRED!" 位于系统中吗? 不在, 所以继续.
    N最大([N]+1).
    # 这个式子在系统看来, 被识别为 "N最大(CON 0+1)."
    # 调用 "N最大" 这个命题, 这是一个全称命题, 需要检查其前提. 将参数填入命题的前提部分, 得到 "CON 0+1是整数". 找到了.
    # 将参数填入结论部分, 得到"!(CON 0+1>CON 0)", 将其加入系统.
    # 进行检查: "A_CONFLICT_HAS_OCCURRED!" 位于系统中吗? 不在, 所以继续.
    冲突([N]+1>[N]).
    # 这个式子在系统看来, 被识别为 "冲突(CON 0+1>CON 0)"
    # 调用 "冲突" 这个命题, 这是一个全称命题, 需要检查其前提. 将参数填入前提, 得到 "CON 0+1>CON 0" 和 "!(CON 0+1>CON 0)", 全部找到. 
    # 将参数填入结论, 因为没有找到大括号, 什么也不干. 直接将 "A_CONFLICT_HAS_OCCURRED!" 填入系统. 
    # 进行检查: "A_CONFLICT_HAS_OCCURRED!" 位于系统中吗? 找到了, 发生矛盾, 假设错误.
    # suppose end.
  # 将 "!(exist: num): {num}是整数, ((any: m) {m}是整数: !({m}>{num}))" 加入系统. 
  # 进行检查: "!((exist: num): {num}是整数, ((any: m) {m}是整数: !({m}>{num})))" 位于系统中吗? 找到了, 证明完毕.
  # proved.
# 将命题 "没有最大整数" 和事实 "(any:): !((exist: num): {num}是整数, ((any: m) {m}是整数: !({m}>{num})))" 加入系统. 
```

# WLS 第一代解释器 ConTab 震撼发布

在以前, 解释器和语言标准分不清. 现在彻底分家了, 解释器是解释器, 语言标准是语言标准. 

解释器有自己的实现, 也在语言标准没有规定的地方可以有自己的发挥. 

由于 ConTab 目前尚为史山代码, 其是否实现了 WLS 的标准并不清楚. 不过, WLS 可能本身就有设计上的问题, 要是出现了一致性缺陷, 需要从语言标准上修改. 

这外面现在全是 ConTab 的代码, 一点 WLS 都没有. 

已知的特性: 

- console 模式下, 如果一次输入多行内容, 似乎会导致错误解析. 
- 文件模式下, 只会读取到倒数第二行. 只要最后一行有注释或者空行就可以. (强制你养成好习惯).
